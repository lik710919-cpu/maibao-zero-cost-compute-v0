# V6（第六版）自愈多来源算力池设计

## 目标

在 V5（第五版）自适应多来源算力池之上增加真正的缺片自愈：当一个已规划的正式分片在首次执行阶段失败时，不重跑完整任务，只识别并重算缺失分片，并使用预留的第二来源预算完成跨来源接管。

## 已冻结基础

- V5（第五版）主分支基线提交：`d8311aa13e1bf0b3131d6f62537672f48f78ab18`。
- V5（第五版）已证明自动分 8 片、来源身份校验、最终合并校验、本机正式计算为 0%。
- V1（第一版）已有 `plan_repairs.py`（缺片修复规划器）用于识别缺失或无效分片。
- Wandbox（在线编译与执行服务）继续作为低负载共享实验来源，每次验收最多承担 1 个正式计算分片。
- V1–V5（第一版到第五版）既有实现不得被破坏；V6（第六版）优先新增独立工作流与最小复用模块。

## 核心设计

### 1. 首次计划与备用预算

V6（第六版）仍自动把 `n=800000` 的工作负载拆成 8 个分片，但首次执行阶段的 8 个分片全部计划给 `github-actions-public`（GitHub 自动化执行服务公开来源）。`wandbox-public`（Wandbox 公开来源）的单次正式计算预算保持完全未使用，作为修复阶段的预留预算。

这样做的目的不是改变 V5（第五版）的常规调度策略，而是建立一条独立的自愈验收路径，证明第二来源能够在首次来源失效后接管缺失工作。

### 2. 受控故障注入

V6（第六版）验收固定把分片索引 `4` 设为故障注入目标。该分片在正式计算函数执行前失败，因此：

- 不产生伪造或半完成结果；
- 不上传该分片的有效首次结果；
- 其他 7 个分片继续正常完成；
- 故障是可重复、可验证、不会随机影响其他分片的受控故障。

故障注入仅存在于 V6（第六版）验收工作流，不进入 V5（第五版）常规工作流。

### 3. 缺片识别

新增面向多来源结果的修复规划器，复用 `compute_chunk.py`（分片计算器）的范围与独立公式校验逻辑，并从现有 `plan_repairs.py`（缺片修复规划器）复用“逐索引验证、只返回缺片”的原则。

修复规划器必须满足：

- 7 个有效首次结果只出现一次时不得进入修复列表；
- 缺失索引 `4` 必须成为唯一修复索引；
- 重复、范围错误、结果错误、来源身份与首次计划不一致的结果必须被视为无效并进入修复；
- 如果没有缺片，修复矩阵使用哨兵值而不产生正式计算；
- 修复规划阶段本身只做验证和调度，不承担正式算力任务。

### 4. 跨来源修复调度

修复调度器接收：

- 缺失分片索引；
- 首次计划中该分片的原来源；
- 当前可用来源目录；
- 每个来源在本次运行中的已用正式任务数量；
- 每个来源的单次任务预算。

修复时必须选择与原来源不同、仍然健康、已授权、零现金成本且剩余预算大于 0 的来源。V6（第六版）验收中唯一合法选择应为 `wandbox-public`（Wandbox 公开来源）。

如果没有合法备用来源，系统必须失败关闭，不能偷偷改用本机、不能重新把缺片派回已失败来源、不能虚构成功结果。

### 5. 修复执行

修复作业只执行修复矩阵里的缺失索引。对于 V6（第六版）验收，正式修复请求必须满足：

- 仅索引 `4` 被重算；
- 实际执行来源为 `wandbox-public`（Wandbox 公开来源）；
- 结果标记为修复结果，而不是首次结果；
- 记录原计划来源 `github-actions-public`（GitHub 自动化执行服务公开来源）和实际修复来源 `wandbox-public`（Wandbox 公开来源）；
- Wandbox（在线编译与执行服务）正式计算请求总数保持为 1。

### 6. 最终聚合

最终聚合使用 7 个有效首次结果加 1 个有效修复结果组成完整 8 片结果集。不得重算或替换其他 7 个正常分片。

最终验证必须证明：

- `worker_count`（有效分片数）为 8；
- `primary_valid_count`（有效首次结果数）为 7；
- `repaired_result_count`（修复结果数）为 1；
- `recovered_indexes`（恢复分片索引）严格等于 `[4]`；
- 首次来源计数为 GitHub（代码托管平台）7 个有效结果；
- 修复来源计数为 Wandbox（在线编译与执行服务）1 个有效结果；
- `combined_sum`（合并总和）等于独立闭式公式的 `expected_sum`（期望总和）；
- `cross_provider_closed`（跨来源闭环）为 `true`（是）；
- `local_formal_compute_percent`（本机正式计算占比）为 `0`；
- 7 个未失败分片没有第二份修复结果。

## 工作流结构

新增 `.github/workflows/zero-cost-compute-v6.yml`（V6 第六版工作流），包含以下阶段：

1. `tests`（测试）：运行完整单元测试。
2. `plan`（规划）：生成 8 个首次 GitHub（代码托管平台）分片计划和 1 个预留 Wandbox（在线编译与执行服务）修复预算。
3. `primary-workers`（首次分片执行）：并行执行 8 个首次分片，其中索引 `4` 受控失败；失败注入不得让整个矩阵提前取消其他分片。
4. `repair-plan`（修复规划）：下载已成功的首次结果，识别唯一缺片索引 `4`，生成修复矩阵。
5. `repair-workers`（修复分片执行）：只由 Wandbox（在线编译与执行服务）执行索引 `4`。
6. `aggregate`（聚合）：下载首次与修复结果，执行完整合并、来源身份、预算、缺片恢复和本机占比验证，上传永久证据工件。

## 失败关闭规则

以下任一情况必须让 V6（第六版）验收失败：

- 缺片数量不是 1；
- 缺失索引不是 `4`；
- 任一正常首次分片被重复修复；
- 修复来源与原来源相同；
- Wandbox（在线编译与执行服务）正式修复请求超过 1 次；
- 修复结果来源身份与修复计划不一致；
- 完整 8 片范围不能精确覆盖 `1..800000`；
- 合并总和错误；
- 本机承担正式计算；
- 任一来源没有真实当前运行证据却被计入闭环。

## 验收边界

V6（第六版）证明的是“首次分片失败后的跨来源缺片自愈”，不声明以下能力已经完成：

- GitHub Actions（GitHub 自动化执行服务）整个控制面不可用时的独立控制面生存；
- 任意数量连续故障的无限修复；
- Wandbox（在线编译与执行服务）作为高吞吐生产来源；
- 动态加入第三、第四个真实来源后的生产级容量治理。

这些能力继续保留为后续门槛，不得由 V6（第六版）验收结果外推。
