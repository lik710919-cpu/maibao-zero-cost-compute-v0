# 统一授权层 V1 设计

## 1. 最高原则

统一授权层的中心思想冻结为：

> 一次授权，长期使用；除非用户本人明确解除，否则系统不得主动撤销授权，也不得把“重新授权”作为日常工作流的一部分。

这条原则优先于单个平台的实现细节。

## 2. 目标

建设一个可复用的统一授权层，GitLab 只是第一个平台适配器。以后任何需要用户授权的平台，都应优先接入这一公共授权能力，而不是重新实现一套独立授权流程。

用户体验目标：

1. 系统发现某个平台需要授权；
2. 统一授权层发起该平台的官方授权流程；
3. 用户只在官方授权页面确认一次；
4. 系统接收授权结果并验证身份与权限；
5. 凭据进入安全凭据库；
6. 后续项目登记、专用最小权限凭据创建、资源接入、真实验收和长期使用均由系统自动完成；
7. 除非用户明确解除授权，否则不再要求用户重复执行初始授权动作。

## 3. 授权生命周期

统一状态：

- `UNAUTHORIZED`：从未授权或已被用户明确解除。
- `AUTHORIZING`：一次授权正在进行。
- `AUTHORIZED`：授权有效，可长期使用。
- `REFRESHING`：短期访问令牌失效，但系统正在自动续期或更换运行凭据。
- `DEGRADED`：授权关系仍保留，但当前运行凭据暂时不可用，需要自动修复。
- `REAUTH_REQUIRED`：平台本身强制要求用户重新确认，且自动续期无法完成。
- `REVOKED_BY_USER`：用户明确解除授权。

关键规则：

- 访问令牌过期不等于用户授权失效。
- 项目级令牌失效不等于用户授权失效。
- 单个平台接口故障不等于用户授权失效。
- 系统应优先自动续期、重新获取运行凭据、重新建立最小权限凭据。
- 只有平台强制要求重新交互确认时，才进入 `REAUTH_REQUIRED`。
- 只有用户本人明确执行解除动作，系统才进入 `REVOKED_BY_USER` 并永久停止使用该授权关系。

## 4. 两层授权模型

### 4.1 用户级长期授权

用户只做一次官方授权。

保存内容仅包括授权关系和安全凭据引用，不把密码、访问令牌或刷新令牌写入代码仓库、普通日志或证据文件。

用户级授权主要用于：

- 确认账户身份；
- 查询授权范围；
- 创建或修复项目级专用凭据；
- 必要时刷新长期授权；
- 执行用户明确允许的平台管理动作。

### 4.2 机器级最小权限授权

日常生产尽量不直接使用用户级高权限凭据。

系统在用户级授权成功后，为具体用途创建权限更小的运行凭据，例如：

- 流水线触发令牌；
- 只读结果查询令牌；
- 项目访问令牌；
- 服务账户；
- 平台允许的其他最小权限凭据。

运行凭据可以自动轮换、自动重建或单独撤销，而不影响用户长期授权关系。

## 5. 公共组件

### 5.1 AuthorizationCore

平台无关的授权核心，负责：

- 创建授权会话；
- 跟踪授权状态；
- 保存非秘密授权登记信息；
- 选择平台适配器；
- 调用凭据库；
- 自动续期；
- 自动修复；
- 明确解除授权；
- 向上层提供统一的“当前是否可执行”结果。

### 5.2 ProviderAuthAdapter

所有平台适配器实现统一接口：

- `begin_authorization()`
- `poll_authorization()`
- `validate_identity()`
- `inspect_scopes()`
- `refresh_authorization()`
- `create_runtime_credentials()`
- `validate_runtime_credentials()`
- `revoke_runtime_credentials()`
- `revoke_user_authorization()`

平台差异只能进入适配器，不进入授权核心。

### 5.3 CredentialVault

统一凭据库接口。

首期 Windows 环境优先接系统安全凭据存储。授权核心只保存凭据引用，不保存明文秘密。

接口至少包括：

- 写入秘密；
- 读取秘密；
- 更新秘密；
- 删除秘密；
- 检查秘密是否存在；
- 返回不含秘密内容的引用编号。

### 5.4 AuthorizationRegistry

只保存非秘密元数据：

- 平台编号；
- 授权账户标识；
- 授权状态；
- 授权时间；
- 最后验证时间；
- 授权范围摘要；
- 凭据引用编号；
- 运行凭据引用编号；
- 绑定资源/项目；
- 是否完成真实验收；
- 最后一次异常类型；
- 是否由用户明确解除。

### 5.5 CapabilityActivator

授权成功后立即推进实际能力，不让授权停在“已登录”状态。

统一流程：

授权成功 → 建立运行凭据 → 登记资源 → 执行真实最小任务 → 验证证据 → 激活能力。

## 6. GitLab 首个适配器

GitLab 作为第一条真实验证线路。

首期目标：

1. 通过 GitLab 官方支持的交互授权方式完成一次用户确认；
2. 获取长期可维护的授权关系；
3. 自动确认当前账户身份；
4. 自动创建或选择授权项目；
5. 自动建立最小权限流水线触发凭据和只读结果凭据；
6. 凭据进入统一凭据库；
7. 调用现有 GitLab 控制器执行一个真实外部分片；
8. 通过现有结果验证；
9. 将 `gitlab-hosted-runners` 从 `adapter_ready` 提升为 `live_active`。

GitLab 适配器不得把平台专用逻辑写入授权核心。

## 7. “一次授权长期使用”的技术语义

该原则不是指平台发出的每个短期访问令牌永不过期，而是指：

> 用户的长期授权关系持续存在；底层短期凭据的过期、刷新、轮换和项目级凭据重建由系统自动处理，不把这些底层生命周期暴露成反复的用户授权动作。

因此：

- 短期令牌可自动刷新；
- 运行令牌可自动重建；
- 项目可自动重新绑定；
- 平台临时故障可自动恢复；
- 凭据损坏可通过长期授权自动修复；
- 只有平台真正要求再次由用户确认时，才请求一次新的官方授权；
- 用户明确解除后，必须停止自动续期、停止凭据重建并清理相关运行凭据。

## 8. 撤销规则

撤销必须是用户明确动作。

解除授权时：

1. 标记 `REVOKED_BY_USER`；
2. 停止该平台所有新的副作用操作；
3. 撤销项目级运行凭据；
4. 删除本地凭据库中的相关秘密；
5. 尽可能调用平台官方撤销接口；
6. 保留不含秘密的审计记录；
7. 以后不得自动恢复，除非用户重新发起一次新的授权。

## 9. 安全边界

- 密码永不进入统一授权层。
- 明文令牌不进入 Git 仓库。
- 明文令牌不进入验收证据。
- 明文令牌不进入普通日志。
- 不通过聊天框传递长期秘密。
- 运行凭据默认最小权限。
- 不自动提升权限范围。
- 权限不足时必须失败关闭。
- 用户明确撤销拥有最高优先级。

## 10. 可复用验收标准

V1 不仅要证明 GitLab 能工作，还必须证明架构确实可复用。

验收至少包括：

1. 授权核心测试不依赖 GitLab 专用字段；
2. GitLab 仅通过 `ProviderAuthAdapter` 接口接入；
3. 凭据库可替换；
4. 短期凭据过期能够自动恢复，不改变用户授权状态；
5. 运行凭据损坏能够通过长期授权自动重建；
6. 用户明确撤销后系统不会自动恢复；
7. 第二个平台可以在不修改 `AuthorizationCore` 的前提下新增适配器并通过公共合同测试；
8. GitLab 完成一次真实授权后的外部分片执行与正式激活；
9. 所有秘密均未进入仓库、测试输出和证据制品。

## 11. 与分布式算力池的关系

统一授权层是公共基础设施，不属于某一个具体算力平台。

后续资源扩张循环变为：

发现平台 → 判断需要授权 → 调用统一授权层 → 用户一次确认 → 自动登记 → 自动生成最小权限运行凭据 → 真实验收 → 激活资源 → 长期复用。

这样每完成一个新的平台授权适配器，就直接降低下一个平台的接入成本，形成能力复利。

## 12. 强制统一入口与强制介入规则（冻结）

统一授权层不是可选工具，而是所有可长期授权平台的强制授权入口。

### 12.1 强制归口

只要某个平台同时满足：

1. 需要用户或账户授权；
2. 平台提供一次交互后可持续使用的授权关系，或能通过刷新令牌、系统钥匙串、服务身份等机制维持长期授权；

则该平台必须进入 `UnifiedAuthorizationService / AuthorizationCore`，不得另建私有登录脚本、旁路令牌文件、独立授权数据库或长期人工复制凭据流程。

### 12.2 三重强制介入

系统必须在三个位置主动拦截，而不是依赖施工人员记忆：

1. **资源发现时拦截**：候选平台一进入资源目录，就必须自动判定授权路线。
2. **适配器注册时拦截**：支持长期授权的平台若未注册到统一授权核心，禁止注册独立授权适配器或继续施工。
3. **能力激活前拦截**：正式登记、运行凭据创建、真实验收和能力激活前必须再次检查统一授权登记状态；未通过统一授权者直接失败关闭。

### 12.3 授权路线

统一使用四类机器状态：

- `UNIFIED_REQUIRED`：确认支持长期授权，必须走统一授权中枢；禁止旁路。
- `DISCOVERY_REQUIRED`：是否支持长期授权尚不明确；先研究，期间禁止建立私有授权旁路。
- `EXCEPTION_ALLOWED`：已确认平台技术上不支持可持续的一次授权关系，才允许进入受控例外流程。
- `NOT_REQUIRED`：平台本身无需授权。

默认必须失败关闭：当平台需要授权但“是否支持长期授权”尚未被证明时，不得默认当作 `EXCEPTION_ALLOWED`，必须进入 `DISCOVERY_REQUIRED`。

### 12.4 防绕行

“有统一授权门但实际没从这个门进入”视为验收失败。

以下行为必须被机器门禁拒绝：

- 对 `UNIFIED_REQUIRED` 平台请求 `private_script` 或其他私有授权路线；
- 在未完成授权能力研究时给 `DISCOVERY_REQUIRED` 平台注册授权适配器；
- 支持长期授权的平台绕过统一登记册直接创建长期运行凭据；
- 未处于 `AUTHORIZED` 状态的平台进入正式能力激活；
- 用户已明确撤销后通过自动修复、重建令牌或其他旁路恢复执行权。

### 12.5 自动接入原则

未来资源发现器发现新平台后，应自动执行：

发现候选 → 判断是否需要授权 → 研究长期授权能力 → 自动生成授权路线 → 若为 `UNIFIED_REQUIRED` 则登记平台适配器 → 用户仅进行一次官方确认 → 自动建立/修复运行凭据 → 真实验收 → 激活。

因此，“统一授权”必须成为资源接入流水线的一部分，而不能依赖人工另外记得执行。

### 12.6 强制验收

最终验收必须额外证明：

1. 资源增长报告会给每个候选输出授权路线；
2. 支持长期授权的平台被自动归入 `UNIFIED_REQUIRED`；
3. 未知平台进入 `DISCOVERY_REQUIRED` 并被阻止走旁路；
4. 私有授权旁路测试真实失败；
5. 未统一授权的平台无法激活；
6. 第二个平台只新增适配器与平台声明即可复用授权核心；
7. 用户明确撤销后即使远端平台暂时不可达，本地也永久失去执行权；
8. 任何失败路径都不得泄漏密码、OAuth 令牌、刷新令牌或运行凭据。
